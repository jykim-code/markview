## 1. 완료된 주요 기능 (현재 라이브)

- ✅ MD 업로드 → 렌더링 페이지 + 공유 URL 생성
- ✅ GFM · 코드 구문 강조 · TOC · LaTeX 수식 · Mermaid 다이어그램 렌더링
- ✅ View / Edit 모드, Edit 실시간 프리뷰, 서버 저장
- ✅ Export (Markdown / HTML / PDF)
- ✅ 다크 / 라이트 모드 (v0.2, 2026-03-24)
- ✅ 포인트 컬러 디자인 (`#FFF7E6`, `#0A122A`)
- ✅ **HTML 문서 지원** — 자기 완결형(인라인 CSS/JS/data-URI, 중첩 iframe) HTML을 샌드박스 iframe으로 렌더링
- ✅ **본문 R2 저장 전환 + 업로드 한도 25MB** (2026-07-22) — 본문을 Cloudflare R2에 저장(D1은 메타데이터만)해 D1 행당 ~2MB 한계를 회피. MD·HTML 공통 25MB
- ✅ 브라우저 확장 프로그램 — Chrome/Edge 사이드 패널 렌더링, 로컬 `.md` file:// 리다이렉트, 원격 `.md` 인터셉트
- ✅ **소유 증명(`owner_token`) + 내 문서 목록(`/my`) + 삭제** (2026-07-30, P0) — 업로드 응답으로 문서당 토큰을 한 번 발급하고 브라우저 localStorage에 보관(`src/lib/myDocs.ts`). `/my`가 그 목록을 화면에 뿌려 **링크 분실 문제를 계정 없이 해결한다.** 삭제는 `X-Owner-Token` 헤더로 소유 증명을 요구하고, 편집(`PUT`)은 정책대로 열어둔다. D1에는 토큰의 SHA-256 해시만 저장
- ✅ **직전 버전 1개 보관 + 되돌리기** (2026-07-30, P0) — 덮어쓰기 전 본문을 R2 `_prev/{slug}`에 복사하고 되돌리기로 교환(두 번 누르면 원래대로). 편집이 열려 있는 정책의 안전장치
- ✅ **본문 글자 크기 조절 (A− / A+)** (2026-08-18) — MD 뷰 헤더에 5단계(90 / 100 / 115 / 130 / 150%) 컨트롤. 모바일에서 글자가 작아 읽기 불편하다는 피드백(2026-07-30)의 절반을 먼저 해결한다. `--reader-font-scale` CSS 변수 하나로 `.prose`를 스케일하고 내부 크기는 `em`이라 제목·코드가 같은 비율로 따라간다. 설정은 localStorage에 남고, 테마와 같이 하이드레이션 전에 적용해 화면이 튀지 않는다. HTML 뷰는 원본 레이아웃 보존 원칙대로 제외. **핀치 확대 시 리플로우는 별건으로 남아 있다**(§3 P2)
- ✅ **되돌리기 크기 제한 철회 — 업로드 한도(25MB)까지 전부 지원** (2026-08-18) — 당초 5MB 초과 본문은 보관을 건너뛰었는데, 그 사이 크기의 문서가 안전장치 없이 편집되고 낡은 슬롯 때문에 '직전'이 아닌 버전이 복원되는 결함까지 있었다(`docs/P0_설계.md` §9 F1·F2·F3). 백업 복사를 `arrayBuffer()` 버퍼링에서 스트리밍(`existing.body`)으로 바꿔 상한을 없앴다 — **되돌리기 지원 범위와 업로드 한도가 같아져 두 숫자가 어긋날 여지가 없다**
- ✅ **모바일 헤더 반응형(햄버거) + 가로 오버플로 버그 수정** (2026-07-22) — 좁은 화면에서 헤더 컨트롤이 뷰포트 폭을 넘쳐 가로 스크롤바와 우측·하단 여백이 생기던 버그 해결. MD/HTML 뷰 공통 헤더를 `EditorHeader`로 추출하고, `md` 미만에서 저장·Export·공유·테마·스크롤 동기화를 햄버거 드롭다운으로 수납 + 루트에 `overflow-x` 가드 추가

## 2. 제품 방향 (2026-07-30 확정)

**대외 — 누구나 쓰는 공개 공유 도구.** 로그인 없이 파일 올리면 링크가 나오는 지금의 흐름을
기본값으로 유지한다. 로그인은 선택이며, 문서를 관리하려는 사람만 한다. 가볍게 쓰다가
필요해지면 업무에서 제대로 쓸 수 있는 구조.

**사내(한컴) — 같은 서비스를 세 경로로 도입.** 별도 사내 버전을 만들지 않는다.
① **MCP 서버로 Claude 산출물 즉시 발행 — 회사 공식 AI가 Claude이므로 주 경로**,
② 웹 링크 공유, ③ Google Chat 봇으로 `.md` 첨부 자동 변환.

### 로그인을 넣는 이유

문서를 많이 올려 공유하다 보면 **정작 본인이 그 링크를 다시 찾지 못한다** (2026-07-30 사용자
피드백). 그러니 풀어야 할 문제는 인증이 아니라 "내가 올린 문서 다시 찾기"다. 익명 상태에서도
최근 문서 목록이 보여야 하고, 로그인은 그 목록을 기기 간에 이어주는 역할이다.

### 편집 권한 정책 (2026-07-30 확정)

**편집은 기본적으로 열어둔다.** 링크를 받은 사람도 직접 고쳐서 보고 싶을 수 있고, 그게 지금의
가벼운 사용 흐름이다. 문서는 하나뿐이므로 누가 고치면 링크 가진 모두가 바뀐 내용을 본다.

| 문서 상태 | 편집 (`PUT`) | 삭제 (`DELETE`) |
|---|---|---|
| 익명 업로드 | 링크 가진 누구나 (현재와 동일) | **소유 증명 필요** (`owner_token`) |
| 로그인 · 잠금 안 함 | 링크 가진 누구나 | 소유자만 (세션) |
| 로그인 · 잠금 | 소유자 + 6자리 비밀번호 입력자 | 소유자만 (세션) |

동작별로 정리하면 이렇다. **편집은 열고, 문서의 성격을 바꾸는 동작은 닫는다.**

| 동작 | 권한 |
|---|---|
| 열람 | 누구나 |
| 편집 | 링크 가진 누구나 (잠금 시 예외) |
| 되돌리기 | 링크 가진 누구나 — 편집이 열려 있는데 복구만 막으면 망친 문서를 고칠 수 없다 |
| **만료 설정 변경** | **소유 증명 필요** — 링크 받은 사람이 남의 문서 기한을 바꾸면 안 된다 |
| 삭제 | 소유 증명 필요 |

- **삭제는 익명 문서도 막는다.** 편집은 내용이 남으니 되돌릴 여지가 있지만, 삭제는 링크 가진
  아무나 남의 문서를 없앨 수 있게 된다.
- **잠금은 로그인 사용자 전용.** 익명에 허용하면 비밀번호를 잊었을 때 복구할 방법이 없다
  (계정이 없으므로). 로그인 사용자는 세션으로 비밀번호를 바꿀 수 있어 복구 경로가 있다.
  로그인할 이유가 하나 더 생기는 효과도 있다.
- ⚠️ **6자리 비밀번호는 rate limit이 보안의 본체다.** 6자리 숫자는 100만 가지뿐이라 시도
  횟수를 안 막으면 몇 초에 뚫린다. slug당 시도 제한(예: 시간당 5회)이 필수. 저장은 salt +
  해싱 — 6자리는 가짓수가 적어 salt 없이 해싱하면 미리 계산된 표로 역산된다.

### `owner_token`이란 — 소유 증명 토큰 (편집 열쇠가 아니다)

문서마다 하나씩 발급하는 긴 무작위 문자열. 브라우저가 자동으로 보관하며 **사용자는 존재를
모른다.** 편집을 막는 용도가 아니다 (위 정책상 편집은 열려 있다). 쓰이는 곳은 두 군데다.

1. **익명 문서 삭제 권한** — 지울 수 있는 사람이 나임을 증명
2. **계정 귀속** — 로그인 시 익명 문서를 내 계정으로 가져오기

> 초기 논의에서 `edit_key`로 불렀으나, 편집을 열어두기로 결정하면서 편집 통제 역할이 사라져
> `owner_token`으로 이름을 바꿨다. `edit_key`라는 이름은 "편집을 막는 것"으로 오해된다.
>
> **문서 잠금 비밀번호와는 완전히 별개다.** `owner_token`은 기계가 자동으로 다루고,
> 잠금 비밀번호는 사람이 기억해서 입력하고 남에게 알려줄 수도 있는 것이다. 섞지 않는다.

```jsonc
// 지금 — 업로드 응답
{ "slug": "a1b2c3d4", "title": "회의록", "type": "md" }
// → 소유 개념이 없어 링크 가진 누구나 덮어쓰고, 목록도 만들 수 없다.

// 바꾼 뒤
{ "slug": "a1b2c3d4", "title": "회의록", "type": "md",
  "owner_token": "k7Fq2xR9mB4vL1nZ8sD3wY6tH0jC5pA2" }
// → 브라우저가 localStorage에 보관 → 내 문서 목록 + 삭제 권한 + 나중에 계정 귀속
```

### 소유권 설계 — 익명 목록에서 계정으로 이어지는 한 줄기

1. **`owner_token` 발급** — 업로드 응답에 실어주고 `DELETE`가 이 토큰을 요구하게 한다.
2. **익명 문서 목록** — 브라우저가 `{slug, owner_token, 제목, 날짜}` 배열을 localStorage에
   쌓는다. 이 배열을 화면에 뿌리면 그게 "내가 올린 문서" 목록이다. 서버 작업 없이 링크
   분실이 풀린다.
3. **계정 귀속(claim)** — 로그인 시 저장된 `owner_token`들을 서버에 제시해 소유권을 증명하고
   `documents.user_id`로 귀속시킨다. 이후 기기 간 동기화가 된다.

3번에서 `slug`만 보내면 남의 slug를 적어 보내도 통하므로, 증명 수단이 없으면 계정 귀속을
안전하게 만들 수 없다. 1·2번이 같은 코드(업로드 응답 + localStorage)를 건드리니 한 번에
처리한다. 로그인 화면은 "이 브라우저에서 올린 문서 N개를 계정에 연결할까요?"가 되어,
빈 계정을 만들라는 것보다 로그인할 이유가 분명해진다.

> 급하면 `owner_token` 없이 목록만 먼저 낼 수도 있다. 단 그 경우 나중에 계정을 붙일 때
> 익명 문서를 가져올 방법이 없어, 사용자에게 "예전에 올린 문서는 목록에서 사라집니다"를
> 고지해야 한다.

### 인증 방식 — 재검토 중 (2026-07-30, 미결)

한때 "자체 이메일 + 비밀번호"로 정했으나 **아래 플랫폼 제약이 확인되어 다시 열어뒀다.**
다음 착수 전에 이 결정을 먼저 내려야 한다.

#### ⚠️ Cloudflare는 안전한 비밀번호 해싱을 막고 있다

| | |
|---|---|
| workerd PBKDF2 반복 상한 | **100,000회 하드 리밋** — 초과 시 `NotSupportedError` |
| OWASP 권고 (PBKDF2-SHA256) | 600,000회 |
| Workers Free CPU 한도 | 요청당 **10ms** (Paid 기본 30초) |

멀티테넌트 DoS 방어를 위한 의도적 제한이고, 상한을 올려달라는 이슈는
[workerd#1346](https://github.com/cloudflare/workerd/issues/1346)에 2023-10 개설된 뒤 아직 열려
있다. 즉 **이 플랫폼에서 자체 비밀번호를 권고 수준으로 해싱할 수 없다.** bcrypt·argon2는
WASM으로 넣어야 하고, 번들 크기와 CPU 시간을 추가로 감당해야 한다(Free 10ms로는 어려워
Paid가 사실상 필요).

#### 검토한 선택지와 현재 판단

| 안 | 상태 |
|---|---|
| 이메일 매직 링크 (비밀번호 없음) | 기술적으로 가장 깔끔하다(해싱·재설정·rate limit 전부 불필요). **다만 로그인마다 메일을 확인하는 게 번거롭다고 판단해 보류** (2026-07-30) |
| 이메일 + 비밀번호 (PBKDF2 10만) | 구현 가능하나 OWASP 권고의 1/6. 유출 시 크래킹 저항이 약하다 |
| 이메일 + 비밀번호 (WASM argon2) | 보안은 가장 낫다. 번들·CPU 비용, Paid 플랜 필요 |
| Google OAuth **단독** | **제외.** 외부 공개 서비스이므로 Google 계정을 강제하면 그게 없는 사용자가 들어올 수 없다. 나중에 선택지로 *추가*하는 건 가능 |

#### 다음에 확인할 것 — Google Workspace 조직 동의 여부

Google을 (단독이 아닌) 선택지로 넣을 때, 사내 계정으로 로그인이 되는지는 회사 Workspace
관리자 설정에 달렸다. 관리자 콘솔의 **Security → Access and data control → API controls**에서
미설정(unconfigured) 서드파티 앱의 접근 수준을 정하는데, 값에 `BLOCK_ALL`과
**`ALLOW_SIGN_IN_ONLY`**가 있다. 즉 데이터 접근은 막고 **로그인만 허용하는 설정이 따로 있다** —
`openid`/`email`/`profile`만 쓰는 로그인 전용 앱이라면 이 설정으로 통과할 여지가 있다.
`BLOCK_ALL`이면 사내 계정 로그인이 막힌다.

OAuth 클라이언트 자체는 개인 Google Cloud 프로젝트에서 회사 승인 없이 만들 수 있다.
**실제로 막히는지는 테스트 클라이언트로 hancom.com 계정 로그인을 시도해보면 30분 내로
확인된다.** (조사 도중 중단됨 — 이 확인이 남아 있다.)

#### 어느 안이든 공통으로 필요한 것

| 항목 | 비고 |
|---|---|
| 세션 관리 | 쿠키, 만료, 갱신. 웹 표준이라 Cloudflare 종속 없음 |
| 메일 발송 | 매직 링크는 로그인용, 비밀번호 방식은 재설정용 — **어느 쪽이든 필요하다** |
| 계정 귀속(claim) | 위 소유권 설계 3단계 |

**Cloudflare 종속 정리**: 세션·Web Crypto는 표준이고 D1은 SQLite라 이전 가능하다. 실질적인 새
종속은 메일 발송 하나뿐이며, Cloudflare Email Sending(바인딩) 대신 Resend·Postmark 같은
HTTP API를 쓰면 `fetch` 한 번이라 어디서든 그대로 돈다. 문서 본문이 이미 R2에, 메타데이터가
D1에 있어 앱 전체는 이미 Cloudflare에 깊이 묶여 있다 — 인증이 더하는 종속은 그에 비해 작다.

**그래서 반드시 만들어야 하는 것** — Google 로그인이면 안 만들어도 되는 항목들이다.

| 항목 | 비고 |
|---|---|
| 비밀번호 해싱 | Workers 환경이라 bcrypt/argon2 대신 Web Crypto PBKDF2 등 검토 필요 |
| 세션 관리 | 쿠키, 만료, 갱신 |
| 무작위 대입 방어 | 로그인 rate limit |
| **비밀번호 재설정** | **메일 발송 인프라 필요** (Cloudflare Email Sending, Resend 등) |
| 가입 확인 메일 | 위 메일 인프라 재사용. 초기엔 생략 가능 |

⚠️ **비밀번호 재설정을 빼면 안 된다.** 없으면 비밀번호를 잊은 사용자가 문서함을 영구히 잃는다.
이것 때문에 메일 발송 인프라가 결국 필요하며, 자체 로그인의 실질 작업량은 대부분 여기서 나온다.

### 결정해둔 정책

- **만료는 기본 없음. 익명 문서도 영구 보관한다** (2026-07-30 확정).
  - 검토 과정에서 "익명 60일 만료"를 잡았다가 물렀다. 근거가 R2 저장 비용이었는데 계산해보면
    근거가 안 된다 — 무료 한도 10GB에 평균 50KB 문서 20만 개가 들어가고, 100GB를 써도 월
    $1.5다. **링크가 죽는 공유 도구는 신뢰를 잃는다**는 손실이 절약보다 크다.
  - "마지막 열람 후 60일"도 검토했으나 물렀다. 위키·문서에 걸어두는 참고용 링크는 원래 드물게
    열리므로, 하필 가장 오래 살아야 하는 문서가 죽는다.
- **만료는 공유 시점의 선택 기능으로 둔다.** 업로드 화면에는 아무것도 추가하지 않는다 —
  올리는 사람이 그 시점에 기한을 생각할 이유가 없다(혼자 보려고 올리는 경우도 있다). "이 링크를
  남에게 준다"는 의식이 생기는 건 공유하는 순간이다.
  - 공유 버튼은 **지금처럼 한 번 클릭으로 즉시 복사**(`src/components/HtmlEditor.tsx:108`).
    복사 후 뜨는 안내에 "이 링크는 영구 보관됩니다 · 만료 설정"만 노출한다. 가장 자주 하는
    동작을 느리게 만들지 않는다.
  - 선택지: 없음(기본) / 7일 / 30일 / 90일. 민감한 내용을 잠깐만 공유하려는 사람에게는
    필요한 기능이다.
  - **나중에 변경 가능해야 한다** (문서 화면·`/my` 목록). 단 **만료 설정 변경은 소유 증명
    필요** — 편집은 열려 있어도 링크 받은 사람이 남의 문서 기한을 바꾸면 안 된다.
- **자동 정리는 마지막 열람 후 1년.** 목적은 저장 비용이 아니라 ⓐ 스팸·불법 콘텐츠 방치 대비,
  ⓑ 남의 개인정보가 담긴 문서를 무기한 보관하는 위험 회피다. 두 근거 모두 "아무도 안 보는
  문서"를 겨냥하므로 기간을 길게 잡아도 목적이 달성된다. 1년이면 위키 링크가 죽을 위험은
  사실상 없다.
- **삭제할 때 404를 주지 않는다.** D1 행은 남기고 R2 본문만 지워 "이 문서는 만료되어
  삭제되었습니다" 안내를 보여준다(tombstone). 용량의 대부분은 본문이고 메타데이터 행은 수백
  바이트라 정리 효과는 그대로다. 링크를 클릭한 사람이 무슨 일인지 알고 원 작성자에게 다시
  요청할 수 있다.
- ⚠️ **기존 문서에 소급 적용 금지** — 이미 공유된 링크가 끊긴다.
- **로그인 유인에서 만료를 뺀다.** 문서가 죽는다고 압박해 로그인시키는 건 "가볍게 쓰는 도구"
  방향과 어긋난다. 로그인할 이유는 기기 간 문서함 동기화 · 편집 잠금 · 폴더·태그·검색으로 충분하다.
- **MCP 서버가 로그인보다 먼저다** (2026-07-30 결정). 회사 공식 AI가 Claude이므로 사내 도입의
  주 경로. 1단계는 인증 없는 `publish`로 내보내고, 문서함 연동은 로그인 도입 후 붙인다.
- **다만 MCP로 발행한 문서가 가장 잘 사라진다** — Claude가 만들고 링크는 대화창에 묻힌다.
  그래서 익명 문서 목록을 MCP보다 먼저 냈다(2026-07-30 완료, §1). **MCP를 착수할 때
  `publish` 응답도 `owner_token`을 함께 돌려주도록 한다** — 업로드 시점에 한 번만 받을 수 있어서
  나중에 소급할 수 없고, 없으면 그 문서는 영구히 주인이 없어진다.
- **편집을 열어두므로 직전 버전 1개는 남긴다** (2026-07-30 완료, §1). 링크 가진 누구나 고칠 수
  있으면 실수나 장난으로 내용이 지워지는 일이 생긴다. 전체 버전 히스토리(P3) 없이도 덮어쓰기 전
  본문을 R2 `_prev/{slug}`에 복사해두면 "되돌리기" 하나로 대부분의 사고가 복구된다.
  <br>키를 `{slug}/prev`가 아니라 `_prev/{slug}`로 둔 이유는 멀티파일 HTML(P1)이 에셋을
  `{slug}/{경로}`에 저장할 계획이어서다 — `prev`라는 이름의 실제 파일과 구분이 안 된다.

## 5. 현재 제약 사항 (스냅샷)

**웹 앱**

| 항목 | 현황 |
|------|------|
| 인증 | 없음 — URL을 아는 누구나 열람/편집. 로그인은 P1(인증 방식 미결, §2) |
| 편집 개방 | `PUT /api/documents/[slug]`에 검증이 없어 링크 가진 누구나 본문을 덮어쓸 수 있다. **2026-07-30에 이를 기본 동작으로 유지하기로 결정**(§2 편집 권한 정책) — 잠금은 로그인 사용자의 선택 기능으로 추가(P1). 안전장치인 되돌리기는 구현됨 |
| 삭제 권한 | `owner_token` 소유 증명 필요(`X-Owner-Token` 헤더). 토큰 없음·불일치·없는 slug 모두 403으로 통일 — slug 존재 여부가 새지 않는다 |
| 문서 삭제 | 구현됨 — `DELETE /api/documents/[slug]`. D1 행 + R2 `{slug}` + `_prev/{slug}`를 함께 지운다 |
| 문서 목록 | `/my` 구현됨 — 단 **이 브라우저의 localStorage에만 있다.** 기기를 바꾸거나 저장소를 비우면 사라진다. 기기 간 동기화는 계정(P1)이 있어야 한다 |
| 되돌리기 | 직전 1개 보관 구현됨(R2 `_prev/{slug}`, 교환 방식). **크기 제한 없음 — 업로드 한도(25MB)까지 모든 문서가 지원된다**(2026-08-18, 이전 5MB 상한 철회) |
| 기존 문서 소유권 | 2026-07-30 이전에 올라간 문서는 `owner_token_hash`가 NULL이라 **소유자가 없다** — 목록에도 안 잡히고 삭제도 안 된다. 소급 적용 금지 결정(§2)의 결과이며 의도된 동작 |
| 파일 크기 | **MD·HTML 공통 25MB** (2026-07-22 상향, 이전 512KB/2MB) |
| 이미지 호스팅 | 미지원 — 외부 URL만 (R2 인프라는 확보됨) |
| HTML 멀티파일 | 미지원 — 단일 자기완결형 파일만 |
| 문서 만료 | 없음 — 영구 보관. **이를 기본값으로 유지하기로 결정**(§2). 만료는 공유 시 고르는 선택 기능으로 추가하고, 마지막 열람 후 1년 자동 정리만 별도로 둔다 |
| 모바일 | 헤더 햄버거 반응형 적용 완료(2026-07-22). Edit 모드 Split View 모바일 UX는 여전히 미최적화 |
| 모바일 확대 | 글자 크기 조절(A− / A+) 구현됨 — MD 뷰 전용, 90~150% 5단계, localStorage 유지. ⚠️ **핀치 확대 시 리플로우(자동 개행)는 여전히 없음** → 확대하면 좌우 스크롤이 생긴다(P2) |
| 뷰 모드 | 스크롤 뷰만 지원 — 페이지 단위(스와이프) 뷰 없음 |
