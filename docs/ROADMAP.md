## 2. 제품 방향 (2026-07-30 확정)

**대외 — 누구나 쓰는 공개 공유 도구.** 로그인 없이 파일 올리면 링크가 나오는 지금의 흐름을
기본값으로 유지한다. 로그인은 선택이며, 문서를 관리하려는 사람만 한다. 가볍게 쓰다가
필요해지면 업무에서 제대로 쓸 수 있는 구조.

**사내(한컴) — 같은 서비스를 세 경로로 도입.** 별도 사내 버전을 만들지 않는다.
① **MCP 서버로 Claude 산출물 즉시 발행 — 회사 공식 AI가 Claude이므로 주 경로**,
② 웹 링크 공유, ③ Google Chat 봇으로 `.md` 첨부 자동 변환.

### 로그인을 넣는 이유

문서를 많이 올려 공유하다 보면 **정작 본인이 그 링크를 다시 찾지 못한다** (2026-07-30 사용자
피드백). 그러니 풀어야 할 문제는 인증이 아니라 "내가 올린 문서 다시 찾기"다. 익명 상태에서도
최근 문서 목록이 보여야 하고, 로그인은 그 목록을 기기 간에 이어주는 역할이다.

### 편집 권한 정책 (2026-07-30 확정)

**편집은 기본적으로 열어둔다.** 링크를 받은 사람도 직접 고쳐서 보고 싶을 수 있고, 그게 지금의
가벼운 사용 흐름이다. 문서는 하나뿐이므로 누가 고치면 링크 가진 모두가 바뀐 내용을 본다.

| 문서 상태 | 편집 (`PUT`) | 삭제 (`DELETE`) |
|---|---|---|
| 익명 업로드 | 링크 가진 누구나 (현재와 동일) | **소유 증명 필요** (`owner_token`) |
| 로그인 · 잠금 안 함 | 링크 가진 누구나 | 소유자만 (세션) |
| 로그인 · 잠금 | 소유자 + 6자리 비밀번호 입력자 | 소유자만 (세션) |

- **삭제는 익명 문서도 막는다.** 편집은 내용이 남으니 되돌릴 여지가 있지만, 삭제는 링크 가진
  아무나 남의 문서를 없앨 수 있게 된다.
- **잠금은 로그인 사용자 전용.** 익명에 허용하면 비밀번호를 잊었을 때 복구할 방법이 없다
  (계정이 없으므로). 로그인 사용자는 세션으로 비밀번호를 바꿀 수 있어 복구 경로가 있다.
  로그인할 이유가 하나 더 생기는 효과도 있다.
- ⚠️ **6자리 비밀번호는 rate limit이 보안의 본체다.** 6자리 숫자는 100만 가지뿐이라 시도
  횟수를 안 막으면 몇 초에 뚫린다. slug당 시도 제한(예: 시간당 5회)이 필수. 저장은 salt +
  해싱 — 6자리는 가짓수가 적어 salt 없이 해싱하면 미리 계산된 표로 역산된다.

### `owner_token`이란 — 소유 증명 토큰 (편집 열쇠가 아니다)

문서마다 하나씩 발급하는 긴 무작위 문자열. 브라우저가 자동으로 보관하며 **사용자는 존재를
모른다.** 편집을 막는 용도가 아니다 (위 정책상 편집은 열려 있다). 쓰이는 곳은 두 군데다.

1. **익명 문서 삭제 권한** — 지울 수 있는 사람이 나임을 증명
2. **계정 귀속** — 로그인 시 익명 문서를 내 계정으로 가져오기

> 초기 논의에서 `edit_key`로 불렀으나, 편집을 열어두기로 결정하면서 편집 통제 역할이 사라져
> `owner_token`으로 이름을 바꿨다. `edit_key`라는 이름은 "편집을 막는 것"으로 오해된다.
>
> **문서 잠금 비밀번호와는 완전히 별개다.** `owner_token`은 기계가 자동으로 다루고,
> 잠금 비밀번호는 사람이 기억해서 입력하고 남에게 알려줄 수도 있는 것이다. 섞지 않는다.

```jsonc
// 지금 — 업로드 응답
{ "slug": "a1b2c3d4", "title": "회의록", "type": "md" }
// → 소유 개념이 없어 링크 가진 누구나 덮어쓰고, 목록도 만들 수 없다.

// 바꾼 뒤
{ "slug": "a1b2c3d4", "title": "회의록", "type": "md",
  "owner_token": "k7Fq2xR9mB4vL1nZ8sD3wY6tH0jC5pA2" }
// → 브라우저가 localStorage에 보관 → 내 문서 목록 + 삭제 권한 + 나중에 계정 귀속
```

### 소유권 설계 — 익명 목록에서 계정으로 이어지는 한 줄기

1. **`owner_token` 발급** — 업로드 응답에 실어주고 `DELETE`가 이 토큰을 요구하게 한다.
2. **익명 문서 목록** — 브라우저가 `{slug, owner_token, 제목, 날짜}` 배열을 localStorage에
   쌓는다. 이 배열을 화면에 뿌리면 그게 "내가 올린 문서" 목록이다. 서버 작업 없이 링크
   분실이 풀린다.
3. **계정 귀속(claim)** — 로그인 시 저장된 `owner_token`들을 서버에 제시해 소유권을 증명하고
   `documents.user_id`로 귀속시킨다. 이후 기기 간 동기화가 된다.

3번에서 `slug`만 보내면 남의 slug를 적어 보내도 통하므로, 증명 수단이 없으면 계정 귀속을
안전하게 만들 수 없다. 1·2번이 같은 코드(업로드 응답 + localStorage)를 건드리니 한 번에
처리한다. 로그인 화면은 "이 브라우저에서 올린 문서 N개를 계정에 연결할까요?"가 되어,
빈 계정을 만들라는 것보다 로그인할 이유가 분명해진다.

> 급하면 `owner_token` 없이 목록만 먼저 낼 수도 있다. 단 그 경우 나중에 계정을 붙일 때
> 익명 문서를 가져올 방법이 없어, 사용자에게 "예전에 올린 문서는 목록에서 사라집니다"를
> 고지해야 한다.

### 인증 방식 — 자체 이메일 + 비밀번호 (2026-07-30 결정)

Google OAuth는 회사 정책·승인 문제로 복잡해질 수 있어 **자체 로그인으로 시작한다.** Google
Chat 연동(P2, 마지막 순서)에 착수할 때 Google 연결 추가를 다시 검토한다.

**그래서 반드시 만들어야 하는 것** — Google 로그인이면 안 만들어도 되는 항목들이다.

| 항목 | 비고 |
|---|---|
| 비밀번호 해싱 | Workers 환경이라 bcrypt/argon2 대신 Web Crypto PBKDF2 등 검토 필요 |
| 세션 관리 | 쿠키, 만료, 갱신 |
| 무작위 대입 방어 | 로그인 rate limit |
| **비밀번호 재설정** | **메일 발송 인프라 필요** (Cloudflare Email Sending, Resend 등) |
| 가입 확인 메일 | 위 메일 인프라 재사용. 초기엔 생략 가능 |

⚠️ **비밀번호 재설정을 빼면 안 된다.** 없으면 비밀번호를 잊은 사용자가 문서함을 영구히 잃는다.
이것 때문에 메일 발송 인프라가 결국 필요하며, 자체 로그인의 실질 작업량은 대부분 여기서 나온다.

`email`·`profile`만 쓰면 민감 scope가 아니라 동의 화면 검증도 가볍고, 미검증 상태로도 100명까지
테스트된다. **다만 회사가 서드파티 앱 접근을 차단해뒀으면 사내 계정으로 막힐 수 있다** — 이게
실제 위험이고, 테스트 클라이언트로 hancom.com 계정 로그인을 시도해보면 30분 내로 확인된다.

Google로 하면 비밀번호 해싱·가입 확인 메일·비밀번호 재설정·무작위 대입 방어를 전부 안 만든다.
Chat·Drive·Gmail 연동과 인증을 공유하는 이점도 있다.

Google Chat 봇(P2) 착수 시에는 Google 신원이 필요하다. 자체 로그인으로 시작했다면 그때
계정에 Google 연결을 추가하는 형태가 된다 — 흔한 방식이라 어렵지 않다.

### 결정해둔 정책

- **익명 문서는 60일 만료** (2026-07-30 확정), 로그인 문서는 영구 보관. 익명을 무기한
  보관하면 아무도 찾을 수 없는 문서가 R2에 계속 쌓인다. 저장 비용이 잡히고 로그인할 이유도
  하나 더 생긴다.
  ⚠️ **기존 문서에 소급 적용 금지** — 이미 공유된 링크가 끊긴다. 신규 업로드부터 적용하고
  업로드 화면에 만료일을 표시한다. 정리 작업은 Cloudflare Cron Trigger로 처리.
- **MCP 서버가 로그인보다 먼저다** (2026-07-30 결정). 회사 공식 AI가 Claude이므로 사내 도입의
  주 경로. 1단계는 인증 없는 `publish`로 내보내고, 문서함 연동은 로그인 도입 후 붙인다.
- **다만 MCP로 발행한 문서가 가장 잘 사라진다** — Claude가 만들고 링크는 대화창에 묻힌다.
  그래서 P0(익명 문서 목록)이 MCP보다 앞에 있어야 한다. MCP `publish` 응답도 `owner_token`을
  함께 돌려주도록 설계해, 나중에 문서함으로 옮길 수 있게 남겨둔다.
- **편집을 열어두므로 직전 버전 1개는 남긴다.** 링크 가진 누구나 고칠 수 있으면 실수나 장난으로
  내용이 지워지는 일이 생기고, 지금은 되돌릴 방법이 없다. 전체 버전 히스토리(P3) 없이도
  덮어쓰기 전 본문을 R2 `{slug}/prev`에 복사해두면 "직전 버전으로 되돌리기" 하나로 대부분의
  사고가 복구된다. 편집 개방 정책과 같이 간다.

> P0 두 항목의 상세 구현 설계는 **[`docs/P0_설계.md`](./P0_설계.md)** 참조.

| **P0** | **직전 버전 1개 보관 + 되돌리기** | 편집을 링크 가진 누구에게나 열어두는 정책의 안전장치. 덮어쓰기 전 본문을 R2 `{slug}/prev`에 복사 → "직전 버전으로 되돌리기" 버튼. 전체 버전 히스토리(P3)와 별개로 값싸게 구현 가능. **편집 개방과 같이 나가야 한다** — 없으면 실수·장난으로 지워진 문서를 복구할 방법이 없다 |
| **P1** | **markview MCP 서버 (AI 산출물 즉시 발행)** | **회사 공식 AI가 Claude이므로 사내 도입의 주 경로 — 로그인·Google 연동보다 앞에 둔다**(2026-07-30 결정). Claude가 만든 HTML/MD를 MCP `publish` 도구로 바로 공유 링크(`/v/{slug}`)화하고 웹에서 렌더링 열람. **기존 `/api/upload`(CORS 오픈) 재사용 → 얇은 래퍼로 착수 부담 낮음.** 배포는 원격 MCP(Cloudflare Workers) 권장. 단계: ① 인증 없는 공개 `publish` MVP → ② 로그인 도입 후 문서함 연동 |
| P1 | **이미지 업로드** | 현재 외부 URL만 지원. **R2 인프라가 이미 붙어 있어 착수 부담이 낮음** — 본문 저장에 쓰는 `CONTENT` 버킷 활용 가능 |
| **P1** | **로그인 (자체 이메일+비밀번호) + 문서 계정 귀속** | §2 소유권 설계 3단계. **Google OAuth 대신 자체 로그인으로 확정**(2026-07-30) — 회사 정책 문제를 피하고, Google 연결은 Chat 연동(P2) 때 재검토. `documents.user_id` 추가 → localStorage의 `owner_token`으로 기존 익명 문서 연결 → 기기 간 동기화. 로그인 문서는 만료 없음. **비로그인 이용은 그대로 유지.** ⚠️ 비밀번호 재설정용 메일 발송 인프라가 필수 — 실질 작업량이 대부분 여기서 나온다(§2) |

| P1 | **멀티파일 HTML 사이트 지원** | `index.html` + 별도 CSS/JS/이미지/다른 HTML 페이지 참조 구조. 현재는 단일 파일(srcDoc)만 되어 상대경로 에셋이 404. 폴더/ZIP 업로드 → R2에 `{slug}/경로` 저장 → 실제 URL 서빙(iframe `src` 전환) 필요. (2026-07-22 신규 도출) |
| P2 | **Google Chat 봇 연동** | `.md` 첨부 시 Markview URL 자동 생성·회신. 사내 도입 경로이나 **MCP가 주 경로가 되어 P2로 조정**(2026-07-30). 착수 시 Google 신원 필요 → 자체 로그인 계정에 Google 연결을 추가하는 형태가 된다. **이 시점에 Google OAuth 도입을 재검토**(§2) |
| P2 | 내 문서 목록 관리 — 폴더 · 태그 · 검색 | P0의 목록 화면 위에 관리 기능을 얹는 단계. 계정 선행 |
| P2 | 접근 제어 — **열람** 제한 | 비공개 문서, 열람용 링크 비밀번호, 조직 내부 공유 제한. **P1의 편집 잠금과 다른 축이다** — 편집 잠금은 "보기는 되고 고치기만 막음", 이건 "보기 자체를 막음" |
| P2 | **HWP/HWPX ↔ MD 변환** | HWP/HWPX 업로드 → 마크다운 자동 변환(편집·공유 원스톱), MD → HWP/HWPX Export. 국가AI전략위 공공문서 마크다운 전환 정책(2026-03-05) 대응, 한컴 파서 기술 활용 — **전략 항목** |

## 5. 현재 제약 사항 (스냅샷)

**웹 앱**

| 항목 | 현황 |
|------|------|
| 인증 | 없음 — URL을 아는 누구나 열람/편집 |
| 편집 개방 | `PUT /api/documents/[slug]`에 검증이 없어 링크 가진 누구나 본문을 덮어쓸 수 있다. **2026-07-30에 이를 기본 동작으로 유지하기로 결정**(§2 편집 권한 정책) — 잠금은 로그인 사용자의 선택 기능으로 추가. 단 현재는 **되돌리기가 없어** 실수·장난을 복구할 수 없다 → P0의 직전 버전 보관으로 해결 |
| 삭제 권한 | 소유 개념이 없어 삭제 API를 열면 아무나 남의 문서를 지울 수 있다 → P0의 `owner_token`이 전제 조건 |
| 문서 삭제 | API 미구현 — `PUT`만 존재 |
| 문서 목록 | 없음 — slug를 알아야 접근. **업로더 본인도 링크를 잊으면 다시 찾을 수 없다** (2026-07-30 사용자 피드백, §2 참조) |
| 파일 크기 | **MD·HTML 공통 25MB** (2026-07-22 상향, 이전 512KB/2MB) |
| 이미지 호스팅 | 미지원 — 외부 URL만 (R2 인프라는 확보됨) |
| HTML 멀티파일 | 미지원 — 단일 자기완결형 파일만 |
| 문서 만료 | 없음 — 영구 보관. P0에서 **신규 익명 문서 60일 만료** 도입 예정(기존 문서는 소급 적용 안 함) |
| 모바일 | 헤더 햄버거 반응형 적용 완료(2026-07-22). Edit 모드 Split View 모바일 UX는 여전히 미최적화 |
| 모바일 확대 | 핀치 확대 시 리플로우(자동 개행) 없음 → 좌우 스크롤 발생. 글자 크기 조절 UI 없음 |
| 뷰 모드 | 스크롤 뷰만 지원 — 페이지 단위(스와이프) 뷰 없음 |

**확장 프로그램**
