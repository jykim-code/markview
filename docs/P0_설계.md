## 0. 착수 전 확인된 제약

### ⚠️ R2 키 이름을 `{slug}/prev`로 두면 안 된다

로드맵 P1의 멀티파일 HTML이 `{slug}/{경로}` 형태로 에셋을 저장할 계획이다. 직전 버전을
`{slug}/prev`에 두면 나중에 `prev`라는 이름의 실제 파일과 구분되지 않는다.
**`_prev/{slug}`를 쓴다.**

| 용도 | R2 키 |
|---|---|
| 현재 본문 (기존 그대로) | `{slug}` |
| 직전 본문 (신규) | `_prev/{slug}` |
| 멀티파일 에셋 (P1, 예약) | `{slug}/{경로}` |

## 1. 데이터 모델

### 마이그레이션 — `migrations/0003_add_ownership.sql`

```sql
-- 소유 증명 토큰의 SHA-256 해시. NULL = 주인 없음(기존 문서).
ALTER TABLE documents ADD COLUMN owner_token_hash TEXT;
```

- **NULL 허용**이어야 한다. 기존 문서는 소유자가 없다 (ROADMAP §2의 "기존 문서 소급 적용 금지").
- `0002_add_type.sql`은 `NOT NULL DEFAULT`를 썼지만 여기서는 쓰지 않는다.
- `expires_at`·`last_viewed_at`은 만료 기능(P1)에서 추가한다 — §5 참조.

### 토큰을 평문이 아니라 해시로 저장하는 이유

`owner_token`은 세션 토큰과 성격이 같다. D1이 유출되어도 남의 문서를 지울 수 없어야 하므로
**해시만 저장하고 평문은 브라우저에만 둔다.** 128비트 무작위 값이라 salt는 필요 없다
(미리 계산된 표를 만들 수 없다). 6자리 잠금 비밀번호(P1)와 달리 여기서는 salt가 불필요하다.

### 기존 문서는 삭제할 수 없게 된다

`owner_token_hash`가 NULL이면 어떤 토큰과도 일치하지 않으므로 기존 문서는 삭제 API로 지울 수
없다. 소급 적용을 안 하기로 한 결정의 결과이며 받아들인다. 운영상 필요해지면 별도 관리자
경로를 만든다 (P0 범위 밖).

## 2. `src/lib/db.ts` 변경

로컬 dev 폴백(`.local-db.json`)이 있으므로 **모든 함수를 Cloudflare 경로와 로컬 경로 양쪽 다
고쳐야 한다.** `Document` 인터페이스에도 필드를 추가한다.

```ts
interface Document {
  id: string; slug: string; title: string; content: string;
  type: DocType; created_at: string;
  owner_token_hash?: string | null;   // 추가
}
```

### 신규 헬퍼

```ts
const OWNER_TOKEN_BYTES = 32;

export function generateOwnerToken(): string {
  const bytes = crypto.getRandomValues(new Uint8Array(OWNER_TOKEN_BYTES));
  // base64url — URL·헤더에 안전
  return btoa(String.fromCharCode(...bytes))
    .replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/, "");
}

export async function hashOwnerToken(token: string): Promise<string> {
  const digest = await crypto.subtle.digest("SHA-256", new TextEncoder().encode(token));
  return [...new Uint8Array(digest)].map(b => b.toString(16).padStart(2, "0")).join("");
}
```

### 변경할 함수

| 함수 | 변경 내용 |
|---|---|
| `insertDocument` | `ownerTokenHash` 인자 추가 → INSERT 컬럼 확장 |
| `updateDocument` | **덮어쓰기 전 현재 본문을 `_prev/{slug}`로 복사** (§4) |
| `deleteDocument` | **신규** — 토큰 검증 후 D1 행 + R2 `{slug}` + `_prev/{slug}` 삭제 |
| `verifyOwnerToken` | **신규** — slug + 평문 토큰 → 일치 여부 |
| `revertDocument` | **신규** — `_prev/{slug}`와 `{slug}` 교환 (§4) |
| `getOwnedDocuments` | **신규** — `[{slug, token}]` 배열 → 검증 통과한 문서 정보만 반환 (§6) |

`getDocumentBySlug`는 P0에서 손대지 않는다 (만료 검사가 빠졌으므로).

> **레거시 본문 위치 주의**: R2 전환 이전에 만들어진 행은 본문이 D1 `content` 컬럼에 있고
> R2에는 객체가 없다 (`getDocumentBySlug`가 이미 이 폴백을 처리한다, `src/lib/db.ts:161-164`).
> 직전 버전 복사도 **같은 폴백을 거쳐야 한다** — R2만 읽으면 레거시 문서는 복사가 조용히
> 빈 값이 된다.

## 3. API 변경

### `POST /api/upload` — 토큰 발급

`src/app/api/upload/route.ts`

```ts
const ownerToken = generateOwnerToken();
const ownerTokenHash = await hashOwnerToken(ownerToken);

await insertDocument(id, slug, title, content, type, ownerTokenHash);

return Response.json(
  { slug, title, type, owner_token: ownerToken },
  { headers: corsHeaders }
);
```

- 응답에 `owner_token`을 담는 건 **이때 한 번뿐**이다. 이후 조회할 방법이 없다.
- **업로드 화면에는 아무 옵션도 추가하지 않는다** (ROADMAP §2) — 파일을 던지면 링크가 나오는
  흐름을 그대로 유지한다. 만료 선택은 공유 시점에 노출한다(P1).

### `DELETE /api/documents/[slug]` — 신규

토큰은 `X-Owner-Token` 헤더로 받는다. DELETE에 본문을 싣지 않는 편이 깔끔하다.

```ts
export async function DELETE(request: Request, { params }) {
  const { slug } = await params;
  const token = request.headers.get("X-Owner-Token");
  if (!token) return Response.json({ error: "권한이 없습니다." }, { status: 403 });
  if (!(await verifyOwnerToken(slug, token)))
    return Response.json({ error: "권한이 없습니다." }, { status: 403 });
  const ok = await deleteDocument(slug);
  if (!ok) return Response.json({ error: "문서를 찾을 수 없습니다." }, { status: 404 });
  return Response.json({ success: true });
}
```

- 존재하지 않는 slug와 토큰 불일치를 **모두 403으로 통일**할지 검토. 구분하면 slug 존재 여부를
  알려주는 통로가 된다. slug가 8자리 hex(32비트)라 이 통로는 없는 게 낫다 → **403 통일 권장.**

### `PUT /api/documents/[slug]` — 검증 없음, 직전 버전만 추가

**편집은 열어두기로 했으므로 토큰 검증을 넣지 않는다** (§2 정책). 변경은 직전 버전 복사뿐이다.

### `POST /api/documents/[slug]/revert` — 신규

되돌리기도 **누구나** 할 수 있게 한다. 편집이 열려 있는데 되돌리기만 막으면, 남이 망친 문서를
발견한 사람이 고칠 수 없다. 편집 정책과 같은 축으로 맞춘다.

### `POST /api/my-documents` — 목록 검증용 (신규)

`{docs: [{slug, token}]}`을 받아 **검증을 통과한 문서만** 정보를 돌려준다. slug만 받아 존재
여부를 알려주면 slug 대량 탐색에 쓰일 수 있으므로 토큰을 함께 요구한다.

`/api/documents/status`로 두지 않은 이유: 같은 트리의 `[slug]` 동적 라우트와 이름이 겹쳐,
정적 세그먼트가 slug를 가리는 구조가 된다. 지금은 slug가 8자리 hex라 실제 충돌은 없지만
헷갈릴 여지를 남기지 않는다.

## 4. 직전 버전 1개 보관

### 저장 (`updateDocument` 안에서)

```
1. 현재 본문 읽기 (R2 {slug}, 없으면 D1 content 폴백)
2. _prev/{slug}로 스트리밍 복사
3. 새 본문을 {slug}에 put
```

R2에는 서버측 복사 API가 없어 **get + put**을 해야 한다. 즉 저장 1회에 본문 크기만큼 읽기와
쓰기가 추가된다.

> **2026-08-18 개정 — 크기 상한(5MB)을 철회했다.**
>
> 당초 "5MB 이하만 직전 버전을 남기고, 초과 문서는 건너뛰되 UI에 안내를 표시한다"로 잡았으나
> 상한 자체가 결함의 원인이어서 없앴다(§9 F1·F2 해결 기록). 근거는 셋이다.
>
> - **I/O 비용을 과대 평가했다.** 저장은 버튼 클릭(`handleSave`)이고 400ms 디바운스는 프리뷰
>   갱신용이라, 타이핑마다 복사가 도는 게 아니라 사용자가 저장할 때만 돈다.
> - **버퍼링을 스트리밍으로 바꿨다.** `await existing.arrayBuffer()` → `existing.body`.
>   25MB 본문을 JS 문자열로 들면 isolate의 128MB 예산을 크게 먹지만, 스트림 통과는 CPU 시간이
>   아니라 I/O 대기라 50ms CPU 한도에 걸리지 않는다.
> - **업로드 한도와 지원 범위가 같아졌다.** 25MB까지 올릴 수 있는데 되돌리기가 5MB에서 끊기면
>   그 사이 크기의 문서는 안전장치 없이 편집된다. 두 숫자를 하나로 만들어 어긋날 여지를 없앴다.

### 되돌리기 (`revertDocument`)

`_prev/{slug}`를 현재로 올리고, 직전 자리에는 방금까지의 현재를 넣는다(교환). 되돌리기를 두 번
하면 원래대로 돌아온다. 슬롯이 하나뿐이므로 이 동작이 가장 예상에 맞다.

`_prev/{slug}`가 없으면(한 번도 저장 안 된 문서) 404를 돌려주고 UI에서는 버튼을 숨긴다.

## 5. 만료 — P0 범위 밖 (P1 착수용 메모)

**기본값이 "만료 없음"으로 결정되어 P0에서 빠졌다** (ROADMAP §2). 기본이 영구 보관이면 서둘러
만들 이유가 없다. 아래는 P1에서 착수할 때의 설계 메모다.

### 만료의 두 갈래를 구분한다

| 갈래 | 기준 | 목적 |
|---|---|---|
| **선택 만료** | 공유 시 사용자가 고름 (없음/7일/30일/90일) | 민감한 내용을 잠깐만 공유 |
| **장기 자동 정리** | 마지막 열람 후 1년 | 스팸·방치 문서 정리, 개인정보 무기한 보관 회피 |

두 갈래를 별개 컬럼으로 둔다. `expires_at`(선택 만료, NULL=없음)과 `last_viewed_at`(장기 정리
기준). 하나로 합치면 사용자가 고른 기한과 자동 정리 기한이 섞여 어느 쪽 때문에 지워졌는지
알 수 없다.

### 만료 UI는 업로드가 아니라 공유 시점

업로드 화면에는 아무것도 붙이지 않는다. 올리는 사람이 그 시점에 기한을 생각할 이유가 없다.
공유 버튼은 **현재처럼 한 번 클릭으로 즉시 복사**하고(`src/components/HtmlEditor.tsx:108`),
복사 후 뜨는 안내에 "이 링크는 영구 보관됩니다 · 만료 설정"만 노출한다. 가장 자주 하는 동작을
느리게 만들지 않는다.

**만료 설정 변경은 `X-Owner-Token` 검증이 필요하다.** 편집은 열려 있어도 링크 받은 사람이 남의
문서 기한을 바꾸면 안 된다 → `PATCH /api/documents/[slug]/settings`.

### `last_viewed_at` 갱신은 쓰기 횟수를 줄여서

조회마다 D1에 쓰면 부담이 크다. **마지막 갱신이 하루 이상 전일 때만 갱신**하면 쓰기 횟수가
문서 수 수준으로 떨어진다.

### 삭제는 tombstone으로 — 404를 주지 않는다

D1 행은 남기고 R2 본문(`{slug}`, `_prev/{slug}`)만 지운다. 그러면 "이 문서는 만료되어
삭제되었습니다" 안내를 보여줄 수 있다. 용량의 대부분은 본문이고 메타데이터 행은 수백
바이트라 정리 효과는 그대로다. 위키에서 링크를 클릭한 사람이 무슨 일인지 알고 원 작성자에게
다시 요청할 수 있다.

`getDocumentBySlug`가 tombstone 행을 구분해 반환해야 한다 (`null`이 아니라 "만료됨" 상태).

### ⚠️ Cloudflare Pages는 Cron Trigger를 지원하지 않는다

`wrangler.toml:2`가 `pages_build_output_dir`이므로 이 프로젝트는 **Pages** 배포다. Cron Trigger는
Workers 전용이라 정리 작업을 지금 구조에 걸 수 없다.

| 안 | 내용 | 평가 |
|---|---|---|
| **A. 별도 정리 Worker** | `workers/cleanup/`에 Cron Worker를 두고 같은 D1·R2 바인딩 연결. `[triggers] crons = ["0 3 * * *"]` | **권장.** Pages 본체를 안 건드리는 표준적인 방식. 배포 대상이 하나 늘어난다 |
| B. 읽을 때 판정만 | 만료 문서가 R2에 영구히 남는다 | 용량 회수가 안 됨. 단독으로는 부족 |
| C. Pages → Workers 이전 | 본체에서 Cron 사용 가능. Cloudflare가 권장하는 방향 | 방향은 맞지만 별도 항목으로 |

**결론: 읽을 때 판정 + A안 정리 Worker.** 읽을 때 판정은 정확성을(정리가 실패하거나 늦어도
만료된 문서는 안 열린다), 정리 Worker는 용량 회수를 담당한다. 한 번에 처리할 건수에 상한을 두고
여러 번 돌게 한다.

> 참고: `/v/[slug]`는 `generateMetadata`와 `ViewPage`에서 `getDocumentBySlug`를 각각 호출해
> 조회가 2회 일어난다(`src/app/v/[slug]/page.tsx:15,36`). 만료 검사와 `last_viewed_at` 갱신이
> 붙으면 중복이 커지므로, 이때 요청 단위 캐시를 함께 검토한다.

## 6. 클라이언트 — localStorage와 목록 화면

### 저장 형식

```jsonc
// localStorage 키: "markview:mydocs"
{
  "v": 1,                       // 형식 버전 — 나중에 구조가 바뀔 때 필요
  "docs": [
    { "slug": "a1b2c3d4", "ownerToken": "k7Fq…", "title": "회의록",
      "type": "md", "uploadedAt": "2026-07-30T04:12:00Z" }
  ]
}
```

`v` 필드를 처음부터 넣는다. 로그인 도입(P1) 때 이 구조를 읽어 계정으로 옮겨야 하므로,
형식이 바뀌었을 때 구분할 수 있어야 한다. 만료 기능(P1)에서 `expiresAt`이 추가되면 `v: 2`로
올린다.

### 쓰는 지점 — `src/components/UploadZone.tsx`

현재 응답에서 `slug`만 꺼내 쓴다(`src/components/UploadZone.tsx:42`). `owner_token`까지 받아
localStorage에 넣고 나서 이동한다.

```ts
const data = (await res.json()) as {
  error?: string; slug?: string; title?: string; type?: string;
  owner_token?: string;
};
if (!res.ok) { setError(data.error || "업로드에 실패했습니다."); return; }
addMyDoc(data);              // src/lib/myDocs.ts
router.push(`/v/${data.slug}`);
```

`src/lib/myDocs.ts`를 새로 만들어 읽기·추가·삭제·정리를 모은다. localStorage 접근이 여러
컴포넌트에 흩어지지 않게 한다.

### 목록 화면 `/my`

- **클라이언트 전용.** localStorage는 서버에서 읽을 수 없으므로 `"use client"`로 두고
  SSR에서 목록을 만들지 않는다.
- 진입 시 `POST /api/documents/status`로 한 번에 검증 → 서버에 없는 항목(삭제됨)은
  localStorage에서 제거한다. 죽은 링크를 목록에 남기지 않는다.
- 각 항목: 제목, 업로드일, 열기·삭제. (만료 임박 표시는 만료 기능 도입 시 추가)
- 빈 상태 안내에 **"이 목록은 이 브라우저에만 저장됩니다"**를 명시한다. 기기 간 동기화는
  로그인(P1)이 필요하다는 걸 미리 알려야 나중에 불만이 안 생긴다.
- 헤더에 `/my` 진입점을 추가한다. 모바일에서는 기존 햄버거 드롭다운에 넣는다
  (`src/components/EditorHeader.tsx`).

### 편집 화면 표시

편집이 열려 있다는 사실을 사용자가 알아야 한다. `SplitEditor`·`HtmlEditor` 저장 영역에
**"이 링크를 가진 누구나 편집할 수 있습니다"**를 표시하고, `_prev`가 있으면 되돌리기 버튼을
같이 둔다.

## 7. 확장 프로그램

`extension/src/background.ts:77`이 업로드 응답에서 `slug`만 꺼내 쓰므로, 그대로 두면 **확장으로
올린 문서는 영구히 주인이 없어진다** — 나중에 로그인해도 가져올 수 없고 삭제도 못 한다.

최소 조치: `owner_token`을 `chrome.storage.local`에 보관한다. 확장 저장소와 웹 localStorage는
서로 다른 원본이라 목록이 즉시 합쳐지지는 않지만, **토큰을 남겨두면 계정 도입 후 합칠 수
있다.** 지금 안 남기면 그 문서들은 되돌릴 수 없다.

> 확장은 Chrome Web Store 심사 기준으로 판단한다는 방침이 있으므로, 저장소 사용이 늘어나면
> `manifest.json`의 권한과 스토어 설명의 데이터 사용 항목을 함께 점검한다.

### 검증에서 나온 항목 — 2026-08-18 전부 해결

세 항목이 모두 5MB 상한 하나에서 나왔다. 상한을 없애자 F1은 안내할 상황이 사라지고, F3은
두 분기가 같아져 차이가 없어졌다. 남는 것은 F2의 정합성 보강 한 줄이다.

#### F1. 5MB 초과 문서에 안내가 없다 — 설계 미충족 → 해결(항목 소멸)

§4는 상한 초과 문서에 "이 문서는 크기가 커서 되돌리기를 지원하지 않습니다"를 표시하라고 적었지만
**그 문구가 코드에 없다.** `useRevert`가 `available: false`를 받으면 `EditorHeader.tsx:120`이
버튼을 아예 렌더링하지 않는다(`revertAvailable ? … : null`). 사용자는 되돌리기가 왜 없는지 알 수
없고, 큰 문서에는 안전장치가 없다는 사실도 모른 채 편집하게 된다.

> **해결 (2026-08-18)** — 안내 문구를 넣는 대신 상한을 없앴다(§4 개정). 문구는 "안전장치가 없는
> 문서가 존재한다"는 사실을 알리는 것이었으므로, 그런 문서가 없어지면 문구도 필요 없다.
> `EditorHeader.tsx:120`은 그대로 두었다 — 이제 버튼이 안 뜨는 경우는 "아직 한 번도 저장하지
> 않은 문서"뿐이고, 그건 되돌릴 것이 없다는 뜻이라 설명이 필요하지 않다.

#### F2. 보관을 건너뛴 저장이 낡은 직전 버전을 남긴다 — 동작 결함 → 해결

`capturePrevVersion`(`src/lib/db.ts:235`)은 **밀려나는 현재 본문**이 5MB를 넘으면 보관을
건너뛰는데, **기존 `_prev/{slug}`를 지우지 않는다.** 그래서 `hasPrevVersion`은 계속 `true`를
돌려주고 버튼도 그대로 뜨지만, 복원되는 건 "직전"이 아니라 더 오래된 버전이다.

실제로 재현한 순서 (2026-08-10):

| 저장 | 현재 본문 | `_prev` 슬롯 | 비고 |
|---|---|---|---|
| 업로드 | V1 (작음) | 없음 | |
| 저장 1 | V2 (작음) | V1 | 정상 |
| 저장 2 | BIG1 (9MB) | V2 | 밀려난 V2가 작아서 보관됨 — 정상 |
| 저장 3 | BIG2 (9MB) | **V2 그대로** | 밀려난 BIG1이 상한 초과 → 건너뜀 |

이 상태에서 되돌리기를 누르면 직전인 BIG1이 아니라 **V2가 복원된다.** 되돌리기 버튼은 계속
떠 있어서 사용자는 마지막 저장이 취소될 거라 기대하지만, 실제로는 두 단계 전 내용으로 덮인다.
**"되돌리기"라는 이름이 약속하는 것과 다르게 동작하므로 데이터를 잃는 방향의 문제다.**

고치는 방향은 두 가지다. ⓐ 보관을 건너뛸 때 기존 `_prev/{slug}`를 삭제해 버튼이 사라지게
한다(F1의 안내와 같이 가면 일관된다), ⓑ 상한을 없애고 항상 보관한다(I/O 비용을 받아들인다).
ⓐ가 원래 설계 의도에 맞다.

> **해결 (2026-08-18) — ⓑ를 택했다.** ⓐ는 "큰 문서는 되돌릴 수 없다"는 제약을 그대로 두고
> 표시만 정직하게 만드는 안이었는데, I/O 근거를 다시 계산해보니 그 제약을 유지할 이유가 없었다
> (§4 개정). 상한을 없애면 위 재현 표의 저장 3에서 `_prev`가 BIG1로 갱신되어 결함이 원인에서
> 사라진다.
>
> 상한과 무관하게 남는 정합성 구멍 하나는 따로 막았다 — 현재 본문이 R2에도 D1에도 없는 문서를
> 저장하면 백업할 것이 없는데, 이때 낡은 슬롯을 지우지 않으면 같은 증상이 재발한다.
> `capturePrevVersion`이 그 경로에서 `_prev/{slug}`를 삭제한다.

#### F3. 로컬 dev 경로에는 5MB 검사가 없다 — 환경 차이 → 해결(차이 소멸)

`updateDocument`의 로컬 분기(`src/lib/db.ts:219-227`)는 크기와 무관하게
`doc.prev_content = doc.content`를 실행한다. Cloudflare 경로에만 상한이 있어서 **F2가 로컬
dev에서는 재현되지 않는다.** dev 전용 폴백이라 사용자 영향은 없지만, 로컬에서 확인하고 넘어가면
놓치는 종류의 차이다.

> **해결 (2026-08-18)** — Cloudflare 경로의 상한을 없애면서 두 분기가 같은 규칙("저장할 때마다
> 크기와 무관하게 보관")이 되어 차이가 사라졌다. 한쪽에만 상한을 두면 로컬에서 재현되지 않는
> 결함이 생긴다는 것이 F2에서 확인된 사실이므로, 로컬 분기에 그 이유를 주석으로 남겼다
> (`src/lib/db.ts`). 앞으로 어느 한쪽에만 조건을 추가하면 안 된다.
